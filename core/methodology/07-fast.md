## 빠르게 하는 법 — 기계 조회를 한 번에 묶는다

인용 30건짜리 문서를 검증하는 데 16분이 걸렸다. 그 시간을 뜯어보면 이렇다.

```
도구 실행      3초   (0.3%)
모델 사고·왕복 958초 (99.7%)   — 호출 31회 × 평균 31초
```

**도구를 빠르게 만들어도 소용없다.** 줄일 것은 왕복 횟수다.

### 기계로 찾을 것은 한 번에 찾는다

인용마다 `find` 하고 생각하고 또 `find` 하면, 찾는 데 0.1초 걸릴 일에 30초짜리 왕복이 붙는다.
찾을 수 있는 것을 먼저 다 찾아 놓고 판단만 이어서 한다.

```bash
python3 -m refver resolve citations.json --corpus <출처폴더> --document <원문서>
```

넣는 것은 `[{"id": "C01", "claim": "본문이 쓴 문장", "source_id": "E01"}, ...]`.
**`source_id`가 없으면 아무것도 조회하지 못한다.**

한 번에 돌려주는 것.

| 돌려주는 것 | 무엇에 쓰나 |
|---|---|
| 주장이 원문서에 축자로 있는가 | 요약해 옮긴 주장을 걸러낸다 |
| 인용한 출처가 코퍼스에 있는가 | 1단계 FAIL 후보 |
| 주장의 수치가 출처에 몇 번, **어느 줄에** 나오는가 | 0회면 VALUE 불일치. 있으면 그 줄을 읽는다 |
| 같은 수치가 다른 출처에도 있는가 | 자료원 불일치·2차 출처 인용 후보 |

**횟수만 보고 넘어가지 마라.** `24.1이 1회 나온다`는 맞는 말이지만, 딸려 오는 줄이
`Nuclear 24.1 26.0`이면 그건 탄소가격이 아니라 원자력 행이다. 실측에서 이 함정에 두 번
걸렸다. `where`의 줄을 읽고 연도와 지표를 맞춰라.

**묻지 않은 출처는 보지 않는다.** 본문이 A를 근거로 대면서 실제로는 B의 수치를 쓴 경우는
A만 뒤져서는 안 나온다. 자료원이 미심쩍으면 다른 출처도 직접 열어라.

**부재 증거는 여기서 주지 않는다.** 낱말을 기계로 자르면 `모자랐다` `쌓인` 같은 활용형
조각이 나오는데, 출처에 없는 것이 당연한 말이다. 부재가 필요하면 낱말을 직접 골라
`lookup`으로 세고 **0회인 것만** 남긴다.

```bash
python3 -m refver lookup queries.json --corpus <출처폴더>
# [{"source_id":"E01","quote":"확인할 문장"}, {"source_id":"E03","terms":["전기요금","요금"]}]
```

### 인용을 여러 에이전트로 나누는 것은 권하지 않는다

인용 판단은 서로 무관하니 나눠 돌리면 빨라질 것 같다. **재 봤더니 아니었다.**

| | 한 곳에서 | 나눠서 | 나눠서(도구 고친 뒤) |
|---|---|---|---|
| 점수 | **99.01** | 97.02 | 96.25 |
| 벽시계 | **961초** | 1,000초 | 1,407초 |
| 도구 호출 | **31회** | 56회 | 90회 |

나누면 일이 줄지 않고 **늘어난다.** 묶음마다 지침을 다시 읽고 같은 PDF를 다시 열며,
조립하는 쪽은 어차피 순차로 판정을 조정해야 한다. 출처 8개·22쪽 정도면 한 에이전트가
통째로 들고 있는 편이 빠르고 정확하다.

그래도 나눠야 할 만큼 큰 문서라면 **인용 번호로 나눈다. 출처로 나누지 마라.** 출처별로
가르면 담당이 자기 출처만 들고 있어서, 본문이 A를 대면서 B의 수치를 쓴 경우를 통째로
놓친다. 실측에서 그렇게 오판이 났다. 그리고 최종 리포트 조립, 독립 재검증, 문서 전체를
봐야 아는 판단은 나누지 않는다.
