# Orange Check

이미 써 놓은 문서의 **참고문헌과 인용을 검증하는 AI 스킬**입니다.
Claude Code · Claude 앱(Cowork) · OpenAI Codex · ChatGPT for Work에서 같은 방법으로 돌아갑니다.

> **출처가 있다고 해서 그 출처가 본문을 뒷받침하는 건 아닙니다.**
>
> 서지만 훑으면 멀쩡해 보이는 문서도 인용을 하나씩 따져 보면 과확장, 지표명 바꿔치기,
> 엉뚱한 조사에 갖다 붙이기가 나옵니다. 검증할 것의 대부분이 여기 있습니다.

읽는 형식은 `.docx` `.pdf` **`.hwp` `.hwpx`** `.txt` `.md`입니다.
한글 문서도 따로 설치할 것 없이 읽고, 본문은 물론 각주·미주·하이퍼링크까지 빠짐없이 훑습니다.

---

## 무엇이 다른가 — 판정을 규칙에서 끌어냅니다

인용이 적절한지 "느낌"으로 재면 볼 때마다 답이 달라집니다. Orange Check은 판정하기 전에
본문 주장을 **여섯 칸으로 쪼개고, 칸마다 따로 출처와 맞춰 봅니다.**

| 슬롯 | 묻는 것 |
|---|---|
| WHO | 누구에 관한 수치인가 (대상 집단·범위) |
| WHEN | 언제 기준인가 |
| WHAT | 무엇을 잰 지표인가 — **출처가 부르는 바로 그 이름** |
| VALUE | 수치와 단위 |
| DATASET | 어느 조사·자료에서 나왔나 |
| RELATION | 비교·인과의 방향 |

어느 칸이 어긋났느냐가 곧 오류의 종류입니다. 판정은 아래 표대로 정해집니다.

| 맞춰 본 결과 | 판정 | 오류 유형 |
|---|---|---|
| 채운 칸이 모두 일치 | 뒷받침됨 | — |
| VALUE 어긋남 | 뒷받침 안 됨 | 수치 오기 |
| WHO만 어긋남 | 부분적 | 과확장 |
| WHAT만 어긋남 | 부분적 | 지표명 오기 |
| DATASET만 어긋남 | 부분적 | 자료원 불일치 |
| WHEN만 어긋남 | 부분적 | 시점 불일치 |
| 출처가 그 지표를 아예 다루지 않음 | 뒷받침 안 됨 | 무관 |
| 출처가 없음 | 판정 불가 | 환각 |

판정부터 정해 놓고 슬롯을 끼워 맞추는 게 아닙니다. 표를 채우면 판정이 저절로 나옵니다.
덕분에 **심판이 그 판정을 기계로 검산할 수 있습니다.**

그 밖에 이런 규칙을 지킵니다.

- **원문을 직접 엽니다.** 제목이나 초록, 검색 결과 몇 줄만 보고 판정하지 않습니다.
- **쪽과 줄을 짚습니다.** "출처가 그렇게 말한다"로 끝내지 않고, 몇 쪽 몇 줄에 뭐라고
  적혀 있는지 원문 표현 그대로 옮깁니다.
- **없다는 것도 증거입니다.** 출처 전문에 '한부모'가 한 번도 안 나오면
  "저소득 한부모 여성" 주장은 그 출처로 뒷받침되지 않습니다.
- **앞선 판정을 가리고 다시 봅니다.** 처음부터 백지에서 판정합니다(CoVe의 factored 방식).
  자기가 낸 답을 보면서 고치면 같은 오류를 되풀이하기 때문입니다.
- **모르면 모른다고 합니다.** 원문을 못 구했으면 '근거 부족'입니다. 그럴듯한 판정을
  지어내는 것, 그게 바로 이 도구가 막으려는 잘못입니다.

## 설치

**패키지는 하나입니다.** 네 플랫폼이 같은 스킬을 씁니다.
[Releases](https://github.com/myorange-io/orange-check/releases/latest)에서 받으세요.

| 환경 | 받을 것 | 설치 |
|---|---|---|
| **Claude 앱 (Cowork·claude.ai)** | `orange-check.zip` | 스킬 업로드 |
| **Claude Code** | `orange-check-all.zip` | 풀어서 `~/.claude/skills/`에 복사 |
| **OpenAI Codex** | `orange-check-all.zip` | 풀어서 `~/.codex/skills/`에 복사 |
| **ChatGPT for Work** | `orange-check-all.zip` | `SKILL.md`를 프로젝트 지침에 붙여넣기 |

claude.ai는 zip 하나에 스킬 하나만 들어 있어야 받아 줍니다. 하위 스킬까지 쓰려면
`orange-check-extract.zip` 같은 파일을 하나씩 올리세요. 폴더째 복사하는 환경은
`-all.zip` 하나면 네 스킬이 다 들어옵니다. 자세한 절차는 패키지 안 `INSTALL.md`에 있습니다.

### 쓰는 법

검증할 문서를 붙이고 이렇게 부탁하면 됩니다.

```
이 문서 참고문헌 검증해줘. 각 인용이 출처에 맞게 인용됐는지도 봐줘.
```

`report.json`(기계가 읽는 정본)과 `참고문헌_검증리포트.md`(사람이 읽는 것)가 나옵니다.
마크다운은 JSON에서 만들어 내므로 둘이 어긋날 일이 없습니다.

### 왜 하나로 충분한가

처음에는 플랫폼마다 따로 만들었습니다. 그런데 막상 갈라진 대목이 **273줄 가운데 30줄**뿐이었고,
그 30줄은 죄다 실행해 봐야 아는 것들이었습니다. 셸을 쓸 수 있나, 코드가 인터넷에 나갈 수 있나,
독립 에이전트를 띄울 수 있나.

이런 건 빌드할 때 정해 둘 일이 아닙니다. 조직 설정이나 샌드박스 정책이 문서와 얼마든지
다를 수 있으니, **미리 짐작해 박아 두는 것보다 그 자리에서 확인하는 쪽이 정확합니다.**
그래서 스킬이 시작할 때 스스로 확인하고 거기에 맞춥니다.

| | Claude Code | Claude 앱 | Codex | ChatGPT for Work |
|---|---|---|---|---|
| 원문 PDF 자동 취득 | ○ | ○ | 샌드박스 설정에 따라 | **✗ 코드가 인터넷에 못 나감** |
| 독립 재검증 | 서브에이전트 | 눈감기 패스 | 눈감기 패스 | 눈감기 패스 |
| 셸 | ○ | 파이썬만 | ○ | 파이썬만 |

이 표는 **스킬이 실행하면서 알아내는 것**이지 패키지에 새겨 둔 것이 아닙니다.
못 한 일은 리포트의 `run.degraded_reasons`에 남습니다. 무엇을 못 했는지 밝히지 않은
리포트라면 무엇을 했다는 말도 믿기 어려우니까요.

ChatGPT for Work에서는 스킬이 **필요한 원문을 한 번에 모아서 요청**하고, 올라오지 않은
출처는 '근거 부족'으로 남겨 둡니다. 원문 없이 판정을 지어내지 않습니다.

## 스킬 구성

한 덩어리로 두지 않고 단계별로 쪼갰습니다. 한 단계만 손보거나, 중간 결과를 사람이 고쳐
넣고 이어서 돌릴 수 있습니다.

| 스킬 | 하는 일 |
|---|---|
| `orange-check` | 0~6단계 전체 |
| `orange-check-extract` | 인용 빠짐없이 모으기 → `citations.json` |
| `orange-check-support` | 주장과 출처를 맞춰 보고 적절성 판정 |
| `orange-check-judge` | 나온 검증 리포트를 채점 |

---

## 이 저장소는 스킬을 어떻게 고쳐 나가는가

스킬을 잘 만들려면 **그 스킬이 몇 점인지 재 주는 심판**이 있어야 합니다. 그런데 심판도
스킬이니 심판을 채점할 심판이 또 필요합니다. 그 꼭대기를 잘못 만들 수가 없을 만큼
자명하게 만드는 것, 그게 핵심입니다.

```
Layer 0  심판의 심판 — 오류를 심어 둔 벤치마크 + 결정적 채점기
         정답을 우리가 심었으니 정답표가 자명하다. LLM 판단이 끼어들 데가 없다.
Layer 1  심판 — 정답표가 없는 실제 문서를 채점한다
Layer 2  대상 스킬 — 점수를 보고 고친다
```

**정답은 심어서 만듭니다.** `benchmark/spec/`에 가상 국가 "오렌지국"의 출처 8종과 인용
28건을 적어 두고, 그중 18건에 오류를 심었습니다. 과확장·지표명 오기·자료원 불일치·수치
오기·시점 불일치·환각·서지 오기·무관·등급 위반을 두 건씩입니다. 인용 하나에
**딱 한 군데만** 손대서 정답이 흐려지지 않게 했습니다. 나머지 10건은 대조군이라,
여기를 지적하면 오탐입니다.

빌더가 사양 하나에서 코퍼스 PDF와 docx, 정답표를 모두 만들어 내고 **스스로 검사합니다.**
사실 문장이 PDF에 딱 한 번 나오는지, 금지어가 새지 않았는지, 본문이 출처를 그대로
베끼지 않았는지(문자열만 맞춰 봐도 정답을 맞히는 지름길이 생기니까) 확인하고,
하나라도 어긋나면 빌드가 멈춥니다. **빌드가 됐다는 사실만으로 정답표를 믿을 수 있어야**
하기 때문입니다.

```bash
python3 benchmark/build.py       # 사양 → 코퍼스·문서·정답표 (스스로 검사)
python3 benchmark/selftest.py    # 채점기 자신을 시험한다
python3 tools/check.py           # 회귀 게이트 전체
```

채점기가 지키는 공리입니다. `selftest.py`가 돌 때마다 확인합니다.

| 리포트 | 점수 |
|---|---|
| 정답표대로 답함 | **100** |
| 근거를 지어냄 (판정 자체는 정확) | 88 — 핀포인트 실재율 0 |
| 전부 통과시킴 | 45 — **낙제**. 심은 오류를 하나도 못 잡음 |
| 전부 문제라고 외침 | 34 — 대조군 오탐 100% |
| 아무것도 안 함 / 스키마 위반 | **0** |

판정 정확도는 **균형 정확도(macro-recall)**로 잽니다. 그냥 정확도로 재면 전부
"이상 없음"이라고 답한 리포트가 58점을 받습니다. 판정이 정상 쪽으로 쏠려 있어서입니다.

### 실제로 재 본 결과, 그리고 그 한계

통합 패키지로 벤치마크를 직접 돌린 결과입니다(`benchmark/runs/run-b.report.json`).

```
점수 100.00 / 100
  인용 추출     재현 100%  정밀 100%   (각주 4·미주 4 포함 28건 전수, 유령 0건)
  심은 오류     18/18 정확 적발       대조군 오탐 0%
  핀포인트 실재 26/26                 판정 도출 일치 26/26
```

**그런데 첫판에 만점이 나왔다는 건 이 자로는 더 잴 게 없다는 뜻이기도 합니다.** 지금 이
벤치마크로는 더 나아진 것을 잴 수 없고 나빠진 것만 잡아냅니다. 회귀 게이트로는 쓸모가
있지만 개선을 재는 자로는 수명이 다했습니다. 분야가 다르고 더 까다로운 `bench-02`가
있어야 합니다(`benchmark/build.py --bench bench-02`로 바로 붙습니다).

측정이 유효한지도 따로 봤습니다. 수행한 에이전트가 정답표와 사양, 채점기를 열지 않았다는
사실을 트랜스크립트의 도구 호출 기록으로 확인했습니다.

더 값진 건 그 실행이 **점수로는 안 잡히는 결함 다섯 가지를 짚어 줬다**는 점입니다.
심판이 `pattern`을 아예 보지 않아서 '뒷받침됨' 판정에 '수치 오기' 유형이 붙어 있어도
조용했고, 출처가 스스로 좁혀 놓은 범위를 본문이 지우고 인용했을 때 어떻게 할지가
규칙에 없었습니다. 모두 고쳤습니다. **점수만 봐서는 놓치는 대목이 있습니다.**

### 심판이 정답표 없이도 보는 것

실제 문서에는 정답표가 없습니다. 그래도 상당 부분은 기계가 대신 봅니다.

| 검사 | 무엇을 잡는가 |
|---|---|
| 실재 | 근거로 적은 인용문이 그 출처 그 쪽에 정말 있는가 → **지어낸 근거** |
| 부재 | "한 번도 안 나온다"고 한 말이 정말 안 나오는가 → **거짓 부재 증거** |
| 도출 | 슬롯 표에서 그 판정이 규칙대로 나오는가 → **근거 없는 판정** |
| 전수 | 문서에서 다시 뽑은 인용과 리포트가 맞는가 → **누락** |

```bash
python3 -m refver audit report.json --corpus sources/ --document 제안서.docx
```

심판이 눈대중으로 볼 몫이 적을수록 심판은 덜 흔들립니다.

여기에는 규칙이 하나 더 있습니다. **심판이 없는 문제를 지어내는 건 못 보고 넘어가는
것보다 나쁩니다.** 실제로 검색어에 설명이 붙어 있는 걸 "0회라고 주장했다"며 몰아세운
적이 있어서, 애매하면 형식만 지적하고 멈추게 고쳤습니다.

## 저장소 구조

```
core/                   방법론의 원본이 있는 곳
  methodology/          조각조각 나눠 둔 산문 — 고칠 데는 여기뿐이다
  skills/               스킬마다 어떤 조각을 쓸지
  toolkit/refver/       표준 라이브러리만 쓰는 도구상자
platforms/universal.yaml  하나뿐인 프로필 (문자 수 제한, frontmatter 허용 항목)
tools/build.py          core + platforms → dist/  (손으로 쓰는 파일이 아니다)
tools/check.py          회귀 게이트
benchmark/              Layer 0 — 사양·빌더·채점기·자기시험
dist/                   만들어진 것. 직접 고치면 --check 가 잡아낸다
```

`dist/`는 언제 다시 지어도 같은 바이트가 나옵니다.

```bash
python3 tools/build.py --check   # 코어에서 그대로 다시 만들어지는지 확인
```

이 저장소가 전에 겪은 실패가 바로 그것이었습니다. 두 플랫폼용 SKILL.md가 소리 없이
갈라지면서 한쪽에만 있는 규칙이 생겼습니다. 이제 방법론 산문은 `core/methodology/`
한 곳에만 두고, 플랫폼 패키지는 전부 거기서 만들어 냅니다.

## 도구상자만 따로 쓰기

스킬 없이 그냥 써도 됩니다. 따로 설치할 것은 없고 PDF 판독기만 있으면 됩니다.

```bash
export PYTHONPATH=core/toolkit
python3 -m refver probe                                  # 이 환경에서 뭐가 되는지
python3 -m refver read 제안서.hwp --summary               # 본문·각주·미주 건수
python3 -m refver find 출처.pdf "확인할 문장"              # 쪽·줄 (쪽 경계도 넘어서 찾음)
python3 -m refver count 출처.pdf 저소득 한부모            # 안 나오면 그것도 증거
python3 -m refver validate report.json                   # 리포트 계약 검사
python3 -m refver render report.json -o 검증리포트.md      # 사람이 읽을 리포트 만들기
```

### 한글 문서 읽기

가장 아래 계층은 **표준 라이브러리만** 씁니다. ChatGPT 코드 인터프리터는 인터넷이 막혀 있어
`pip install`도 `npm install`도 못 하기 때문입니다.

| 형식 | 읽는 방식 | 각주·미주 |
|---|---|---|
| `.hwpx` | ZIP + OWPML XML | 정확히 갈라냄 |
| `.hwp` (5.x) | OLE2 복합문서 + 레코드 훑기 | 대략 갈라냄 |
| `.hml`, 내용이 XML인 `.hwp` | HWPML | 정확히 갈라냄 |

**실제로 재 봤습니다.** 손에 있던 한글 문서 1,267건 가운데 **93.4%**가 순수 파이썬만으로
열렸습니다. 안 열리는 나머지는 대개 HWP 3.x(옛 이진 형식)인데, 이건 다른 도구도 못 엽니다.

Node가 깔려 있으면 [kordoc](https://github.com/chrisryugj/kordoc)이 거듭니다. 설치 없이
`npx -y kordoc`으로 바로 쓰고, **순수 파이썬이 실패하면 알아서 넘어갑니다.**

| kordoc이 더 해 주는 것 | |
|---|---|
| 표를 표로 살려 냄 | 한국 보고서는 통계가 대개 표 안에 있는데, 순수 파이썬은 문단으로 뭉갭니다 |
| 블록마다 쪽 번호 | 쪽·줄을 짚기가 수월해집니다 |
| 배포용 문서 풀기 · 망가진 CFB 복구 | 순수 파이썬으로는 손도 못 대는 파일 |
| HWPML·PDF·Office까지 한 도구로 | |

**뽑아내는 글자 수는 같습니다.** 실제 파일로 맞춰 보니 한글 글자 수가 정확히 똑같았습니다
(1928 = 1928). kordoc이 나은 건 회수율이 아니라 표 구조와 열 수 있는 형식의 폭입니다.

```bash
python3 -m refver read 문서.hwp --backend kordoc   # 표를 살려서 읽기
```

남이 준 문서를 여는 도구다 보니 XML 엔티티 폭탄, XXE, ZIP 폭탄, 경로 탈출을 먼저
막습니다(`refver/safexml.py`). `defusedxml`이 깔려 있으면 그걸 쓰고, 없으면 DTD나 엔티티
선언이 들어 있는 문서를 아예 거절합니다. 다만 HWPML은 `&nbsp;` 같은 선언을 정상적으로
쓰기 때문에, DTD를 파서에 넘기지 않고 문자 하나짜리 선언만 직접 바꿔치기해서 읽습니다.
