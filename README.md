# Orange Check

이미 작성된 문서의 **참고문헌과 인용을 검증하는 AI 스킬**입니다.
Claude Code · Claude 앱(Cowork) · OpenAI Codex · ChatGPT for Work 네 곳에서 같은 방법론으로 돕니다.

> **출처가 존재한다 ≠ 그 출처가 본문 주장을 뒷받침한다.**
>
> 서지만 확인하면 통과처럼 보이는 문서도, 인용 적절성을 따지면 과확장·지표명 오기·자료원
> 불일치가 드러납니다. 실제 검증의 대부분은 여기서 일어납니다.

검증 대상: `.docx` `.pdf` **`.hwp` `.hwpx`** `.txt` `.md`
(한글 문서는 별도 설치 없이 읽습니다. 본문뿐 아니라 각주·미주·하이퍼링크까지 전수로 훑습니다.)

## 무엇이 다른가 — 판정을 규칙에서 끌어냅니다

인용이 적절한지 "느낌"으로 판단하면 매번 다른 답이 나옵니다. Orange Check은 판정 전에
본문 주장을 **여섯 칸으로 쪼갠 뒤 칸마다 따로 출처와 대조**합니다.

| 슬롯 | 묻는 것 |
|---|---|
| WHO | 누구에 관한 수치인가 (대상 집단·범위) |
| WHEN | 언제 기준인가 |
| WHAT | 무엇을 잰 지표인가 — **출처가 쓰는 바로 그 이름** |
| VALUE | 수치와 단위 |
| DATASET | 어느 조사·자료에서 나왔나 |
| RELATION | 비교·인과의 방향 |

어느 칸이 어긋났는지가 곧 오류의 종류이고, 판정은 규칙표에서 기계적으로 나옵니다.

| 대조 결과 | 판정 | 유형 |
|---|---|---|
| 채운 칸이 전부 일치 | 뒷받침됨 | — |
| VALUE 불일치 | 뒷받침 안 됨 | 수치 오기 |
| WHO만 불일치 | 부분적 | 과확장 |
| WHAT만 불일치 | 부분적 | 지표명 오기 |
| DATASET만 불일치 | 부분적 | 자료원 불일치 |
| WHEN만 불일치 | 부분적 | 시점 불일치 |
| 출처가 그 지표를 아예 다루지 않음 | 뒷받침 안 됨 | 무관 |
| 출처가 존재하지 않음 | 판정 불가 | 환각 |

판정을 정해 놓고 슬롯을 끼워 맞추는 게 아니라, 표를 채우면 판정이 저절로 나옵니다.
이 덕분에 **심판이 판정의 타당성을 기계로 검사**할 수 있습니다.

그 밖에 지키는 것들:

- **원문 직접 판독** — 제목·초록·검색 스니펫으로 판정하지 않습니다.
- **쪽·행 핀포인트** — "출처가 그렇게 말한다"가 아니라 몇 쪽 몇 줄에 뭐라 적혔는지 원문 표현 그대로 인용합니다.
- **부재도 증거** — 출처 전문에 '한부모'가 0회면 "저소득 한부모 여성" 주장은 그 출처로 뒷받침되지 않습니다.
- **독립 재검증** — 앞선 판정을 보지 못하는 상태에서 처음부터 다시 판정합니다(CoVe의 factored 방식). 모델이 자기 오류를 되풀이하는 것을 막습니다.
- **모르면 모른다** — 원문을 못 구했으면 '근거 부족'입니다. 그럴듯한 판정을 지어내는 것이 이 도구가 막으려는 바로 그 잘못입니다.

## 설치

플랫폼별 패키지는 [Releases](https://github.com/myorange-io/orange-check/releases/latest)에서 받습니다.
각 패키지 안의 `INSTALL.md`에 그 환경의 설치 절차가 들어 있습니다.

| 환경 | 패키지 | 요약 |
|---|---|---|
| **Claude 앱 (Cowork·claude.ai)** | `orange-check-claude-app.zip` | 설정 → 기능에서 **코드 실행**을 켠 뒤, Cowork → 맞춤설정 → 스킬 → ＋ → 스킬 업로드 |
| **Claude Code** | `dist/claude-code/` | `cp -R orange-check* ~/.claude/skills/` |
| **OpenAI Codex** | `dist/codex/` | `cp -R orange-check* ~/.codex/skills/` |
| **ChatGPT for Work** | `orange-check-chatgpt-work-all.zip` | `SKILL.md` 내용을 프로젝트 지침에 붙여 넣고, 문서와 **출처 원문을 함께** 첨부 |

zip은 **스킬 하나당 하나**입니다 — 압축을 풀면 `SKILL.md`를 담은 폴더 하나가 나옵니다.
claude.ai 업로드가 그 구조를 기대하기 때문입니다. 네 스킬을 다 쓰려면 zip 네 개를 각각
올리거나, 지침을 통째로 붙여 쓰는 환경에서는 `-all.zip` 묶음을 씁니다.

### 사용

검증할 문서를 첨부하고 이렇게 요청합니다.

```
이 문서 참고문헌 검증해줘. 각 인용이 출처에 맞게 인용됐는지도 봐줘.
```

`report.json`(기계용 정본)과 `참고문헌_검증리포트.md`(사람용)가 나옵니다.
마크다운은 JSON에서 **생성**되므로 둘이 어긋날 수 없습니다.

### 환경별로 달라지는 것

방법론은 같지만 런타임 능력이 다릅니다. 각 패키지는 그 차이를 **정직하게** 반영해 생성됩니다.

| | Claude Code | Claude 앱 | Codex | ChatGPT for Work |
|---|---|---|---|---|
| 원문 PDF 자동 취득 | ○ | ○ | 샌드박스 설정에 따름 | **✗ 코드가 인터넷에 못 나감** |
| 독립 재검증 | 서브에이전트 | 눈감기 패스 | 눈감기 패스 | 눈감기 패스 |
| 셸 | ○ | 파이썬만 | ○ | 파이썬만 |

ChatGPT for Work에서는 스킬이 **필요한 원문 목록을 한 번에 요청**하고, 올라오지 않은
출처는 '근거 부족'으로 남깁니다. 원문 없이 판정을 지어내지 않습니다.

## 스킬 구성

한 덩어리가 아니라 단계별로 쪼개 두었습니다. 한 단계만 손보거나, 중간 결과를 사람이 고쳐
넣고 다시 이어 갈 수 있습니다.

| 스킬 | 하는 일 |
|---|---|
| `orange-check` | 0~6단계 전체 |
| `orange-check-extract` | 인용 전수 수집 → `citations.json` |
| `orange-check-support` | 주장·출처 대조 → 적절성 판정 |
| `orange-check-judge` | 나온 검증 리포트를 채점 |

## 이 저장소는 스킬을 어떻게 개선하는가

스킬을 잘 만들려면 **그 스킬이 몇 점인지 재는 심판**이 있어야 합니다. 그런데 심판도 스킬이라
심판의 심판이 필요합니다. 그 꼭대기를 잘못 만들 수 없을 만큼 자명하게 만드는 것이 핵심입니다.

```
Layer 0  심판의 심판 — 오류를 심은 벤치마크 + 결정적 채점기
         정답을 우리가 심었으므로 정답표가 자명하다. LLM 판단이 없다.
Layer 1  심판 — 정답표 없는 실제 문서를 채점한다
Layer 2  대상 스킬 — 점수를 보고 고친다
```

**정답은 심어서 만듭니다.** `benchmark/spec/`에 가상 국가 "오렌지국"의 출처 8종과 인용 28건을
정의하고, 그중 18건에 오류를 심었습니다(과확장·지표명 오기·자료원 불일치·수치 오기·시점
불일치·환각·서지 오기·무관·등급 위반 각 2건). 인용 하나당 **정확히 한 차원만** 오염시켜
정답이 자명하게 갈리도록 했습니다. 나머지 10건은 대조군이라, 여기를 지적하면 오탐입니다.

빌더가 사양에서 코퍼스 PDF·docx·정답표를 전부 파생하고 **스스로 검증**합니다. 사실 문장이
PDF에 정확히 1회 있는지, 금지어가 새지 않았는지, 본문이 출처를 그대로 베끼지 않았는지
(문자열 일치만으로 정답을 맞히는 반칙 경로) 확인하고, 하나라도 어긋나면 빌드를 실패시킵니다.
**빌드가 성공했다는 사실만으로 정답표를 신뢰할 수 있어야** 하기 때문입니다.

```bash
python3 benchmark/build.py       # 사양 → 코퍼스·문서·정답표 (자기검증)
python3 benchmark/selftest.py    # 채점기 자신을 시험한다
python3 tools/check.py           # 회귀 게이트 전체
```

채점기의 공리 — `selftest.py`가 매번 확인합니다.

| 리포트 | 점수 |
|---|---|
| 정답표대로 답함 | **100** |
| 근거를 지어냄(판정은 정확) | 88 — 핀포인트 실재율 0 |
| 전부 통과시킴 | 45 — **낙제**. 심은 오류 적발 0 |
| 전부 문제라고 외침 | 34 — 대조군 오탐 100% |
| 아무것도 안 함 / 스키마 위반 | **0** |

판정 정확도는 **균형 정확도(macro-recall)**로 잽니다. 단순 정확도를 쓰면 전부 "이상 없음"이라고
답하는 리포트가 58점을 받습니다 — 판정 분포가 정상 쪽으로 치우쳐 있기 때문입니다.

### 실측 결과와 그 한계

Claude Code용 패키지로 벤치마크를 실제 수행한 결과(`benchmark/runs/run-a`):

```
점수 100.00 / 100
  인용 추출     재현 100%  정밀 100%   (각주 4·미주 4 포함 28건 전수, 유령 0건)
  심은 오류     18/18 정확 적발       대조군 오탐 0%
  핀포인트 실재 30/30                 판정 도출 일치 26/26
```

**그런데 첫 시도 만점은 벤치마크가 포화됐다는 뜻이기도 합니다.** 지금 이 벤치마크로는
더 나아진 것을 잴 수 없고, 나빠진 것만 잡아낼 수 있습니다. 회귀 게이트로는 쓸모가 있지만
개선 신호로는 이미 다 쓴 자입니다. 도메인이 다르고 더 어려운 `bench-02`가 필요합니다
(`benchmark/build.py --bench bench-02`로 바로 붙습니다).

측정이 유효한지도 확인했습니다 — 수행 에이전트가 정답표·사양·채점기를 열지 않았음을
트랜스크립트의 도구 호출로 확인했습니다.

그 실행에서 나온 것 중 채점에 잡히지 않은 진짜 결함이 하나 있었습니다. 규칙표의
`direction_only`가 계약 enum에 없고, `tier_violation`·`biblio_mismatch`는 enum에만 있고
규칙표에 행이 없었습니다. **채점은 통과했지만 문서가 스스로 모순됐던 것**이고, 이건
사람(또는 수행 에이전트)이 읽어야만 보입니다. 점수만 보면 놓칩니다.

### 심판이 정답표 없이 보는 것

실제 문서에는 정답표가 없습니다. 그래도 상당 부분은 기계로 검사됩니다.

| 검사 | 무엇을 잡는가 |
|---|---|
| 실재 | 근거로 적은 인용문이 그 출처 그 쪽에 정말 있는가 → **지어낸 근거** |
| 부재 | "0회"라고 한 검색어가 정말 0회인가 → **거짓 부재 증거** |
| 도출 | 슬롯 표에서 그 판정이 규칙대로 나오는가 → **근거 없는 판정** |
| 전수 | 문서에서 다시 뽑은 인용과 리포트가 맞는가 → **누락** |

```bash
python3 -m refver audit report.json --corpus sources/ --document 제안서.docx
```

심판이 판단할 몫이 작을수록 심판은 흔들리지 않습니다.

## 저장소 구조

```
core/                   방법론의 유일한 원본
  methodology/          조각난 산문 — 여기만 고친다
  skills/               스킬별로 어떤 조각을 쓸지
  toolkit/refver/       표준 라이브러리만 쓰는 도구상자
platforms/*.yaml        플랫폼별 능력 프로필(문자 수 제한·셸 유무·네트워크 등)
tools/build.py          core + platforms → dist/  (손으로 쓰지 않는다)
tools/check.py          회귀 게이트
benchmark/              Layer 0 — 사양·빌더·채점기·자기시험
dist/                   생성물. 직접 고치면 --check 가 잡아낸다
```

`dist/`는 바이트 단위로 재현됩니다.

```bash
python3 tools/build.py --check   # 코어에서 그대로 다시 만들어지는지 확인
```

이 저장소가 이전에 겪은 실패가 정확히 그것이었습니다 — 두 플랫폼용 SKILL.md가 조용히
갈라져 한쪽에만 있는 규칙이 생겼습니다. 이제 방법론 산문은 `core/methodology/` 한 곳에만
있고 플랫폼 패키지는 전부 생성물입니다.

## 도구상자 직접 쓰기

스킬 없이도 됩니다. 의존성이 없습니다(PDF 판독기만 있으면 됩니다).

```bash
export PYTHONPATH=core/toolkit
python3 -m refver probe                                  # 이 환경에서 뭐가 되는지
python3 -m refver read 제안서.hwp --summary               # 본문·각주·미주 건수
python3 -m refver find 출처.pdf "확인할 문장"              # 쪽·행 (쪽 경계도 넘어 찾음)
python3 -m refver count 출처.pdf 저소득 한부모            # 0회는 부재의 증거
python3 -m refver validate report.json                   # 리포트 계약 검사
python3 -m refver render report.json -o 검증리포트.md      # 사람용 리포트 생성
```

### 한글(HWP) 판독

| 형식 | 방식 | 각주·미주 |
|---|---|---|
| `.hwpx` | ZIP + OWPML XML, 순수 파이썬 | 정확히 분리 |
| `.hwp` (5.x) | OLE2 복합문서 + 레코드 순회, 순수 파이썬 | 근사 |
| `.hwp`/`.hwpx` + [rhwp](https://github.com/edwardkim/rhwp) | `rhwp export-pdf`로 PDF 경유 | 쪽·행이 한글 뷰어와 일치 |

rhwp가 PATH에 있으면 `read --via-pdf`로 쓸 수 있습니다. rhwp는 MCP 서버도 내장하고 있어
`.mcp.json`에 `{"rhwp": {"command": "rhwp", "args": ["mcp-serve"]}}` 한 줄로 붙일 수 있습니다.

신뢰할 수 없는 문서를 여는 도구이므로 XML 엔티티 폭탄·XXE·ZIP 폭탄·경로 탈출을 먼저
막습니다(`refver/safexml.py`). `defusedxml`이 설치돼 있으면 그것을 쓰고, 없으면 DTD·엔티티
선언이 든 문서를 아예 거부합니다.
